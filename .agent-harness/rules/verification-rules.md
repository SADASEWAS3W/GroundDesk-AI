# 任务级最终验证规则

本规则统一规定三层 Harness 的验证时机；各领域规则和工作流规定验证内容。两者共同适用，不因推迟执行而减少验收要求。

## 任务边界

- 一个任务是用户当前要求交付的完整目标，不是一个文件、实现步骤、阶段汇报或一次工具调用。
- 同一目标的多个阶段共享最终验证计划；阶段切换、进度汇报、对话续接不自动触发新一轮验证。
- 用户明确要求独立交付、提交或部署某个阶段时，该交付边界需要验证；不能替用户默认把每个阶段当作独立交付。

## 三层职责

1. 规范层：实现过程中持续遵守架构、安全、数据和 API 契约；测试执行集中到任务末尾。
2. 编排层：阶段内实现功能、编写测试与文档、累计待验证项；全部阶段完成后，汇总所有适用 Profile 的 `requiredGates` 和领域专项验收项并去重。
3. 自动验证层：在最终交付前执行一次汇总后的验证计划。`scripts/harness/` 中的检查脚本仍可单独调用，但不作为每个阶段的固定收尾动作。

## 默认执行节奏

```text
任务定级与方案 → 阶段一实现 → 阶段二实现 → …… → 文档和测试代码完成
→ 汇总、去重验证计划 → 一轮最终验证 → 交付
```

- 测试代码随实现编写；不要求为阶段验收提前运行测试、真实模型评测、数据库集成测试或完整 Harness。
- 阶段汇报记录“已实现，待最终验证”，列出待验证范围；不将尚未执行的检查写成通过或最终跳过。
- 只读分析或文档任务按其 Profile 在末尾执行适用检查，不因内部拆阶段升级为全套后端、前端、Compose 或付费模型测试。
- 需要 `run-all.ps1`（例如提交前统一门禁）时，将其作为最终计划的一个入口；不要先逐个运行它覆盖的门禁再重复调用它。真实模型评测等未被该入口覆盖的专项验证在同一最终验证轮次补齐。
- 一轮验证可以包含多个命令，不等于只运行一个测试。多个 Profile 中的相同门禁只执行一次，强门禁覆盖弱门禁时也不重复，例如 `compose-full` 覆盖 `compose`。

## 必要检查与失败处理

- 为定位阻塞问题，可以按需执行最小复现或诊断检查，不自动扩展为整套阶段验证。
- 用户明确要求中途运行某项测试时，按其要求执行；仍不自动重复其他门禁。
- 破坏性操作前的目标核对、授权、备份、迁移方案审查，以及实际调用时的密钥隔离、向量维度校验、人工审批等安全前置条件不属于可推迟的阶段验收。
- 最终验证失败时，修复后只补跑失败项与受修复影响的检查；仅在影响范围无法界定时重跑完整计划。
- 验证通过后若修改了被验证的代码、配置、测试或文档，相应验证结果失效，交付前补跑受影响检查。不得为了“一轮”而沿用过期结果。
- 网络、依赖、凭据或费用授权导致未执行时，如实说明阻塞、剩余风险和后续动作。安全的等价补验可替代失败入口的对应检查，但不能把原入口写成执行成功。

本策略不关闭 CI，不绕过提交/发布门禁，不授权真实模型费用、业务数据写入或自动提交。

正式部署或业务数据迁移之前仍须具备对应验证证据；数据库集成检查优先在隔离环境完成，不能把“最后统一验证”解释为先上线或先改生产数据再补测。
